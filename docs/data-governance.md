# Data governance

**Audience.** Judges, participants, and the clinical adviser.

## 1. What data Sila handles

- **Account data:** email and a password hash (argon2id). No name, no address, no phone number.
- **Carrier screening results (synthetic):** generated by `scripts/generate-synthetic.ts` with a fixed seed. Encrypted at rest with AES-256-GCM, per-person data keys wrapped with a key-encryption key (KEK) held only in the deployment's secret store.
- **Partner link data:** one row per invite + acceptance. Holds two user ids, an invite code and a status. No personal detail.
- **Consent rows:** who granted what, to whom, at what scope, when. Revocation sets `revoked_at` and takes effect on the next request.
- **Relatives:** a display name per relative. No identifier, no contact information.
- **Referrals and steps:** priority, created_at, closed_at, and an audit trail of counselling steps. No genetic data.
- **Audit log:** every allowed and denied access to personal data. Append-only at the database level; hash-chained to make tampering detectable.
- **Volunteer data (study mode):** one row per volunteer holding language, reading-comfort band, counterbalance order and an assigned synthetic couple id. **No name, no email, no genetic data.** The participant code is HMAC'd before storage; the raw code only ever appears in the volunteer's own browser.
- **Quiz responses and time-to-referral events (study mode):** scored before and after the explanation; milestone timestamps.

## 2. Consent model

Every disclosure of personal data requires an active consent. Purposes:
- `couple_risk` — both partners must grant it before the couple view is computed.
- `share_with_partner` — scope `conditions_carried` or `full_result`.
- `share_with_relative` — same scopes, named relative.
- `counsellor_access` — per referral, revocable.
- `evaluation_data` — opt-in to include quiz scores (never genetic data) in the evaluation.

A grant can be revoked at any time. The policy check is fresh on every request, so revocation takes effect at once.

## 3. Data minimisation

- No name or contact information is ever collected.
- Volunteers are anonymous. The participant code is never stored raw.
- Dashboards show aggregates only, with every cell n ≥ 5 and no totals that would let a reader infer a hidden cell.
- Error responses carry no stack trace in production.
- Server-side `console` output is redacted for argon2 hashes, 64-hex session tokens, participant codes, panel variant ids and `"password"` keys.

## 4. The audit log

Every allowed and every denied access to personal data writes a row. Rows are:
- Append-only at the database level (a BEFORE UPDATE/DELETE/TRUNCATE trigger refuses the operation).
- Hash-chained (`sha256(prev_hash + canonical_json)`). `npm run audit:verify` walks the chain and reports the first break if any.
- Never contain genetic data.
- Visible to the person they concern via `/access-log`.

The runtime database role (`sila_app`) has `SELECT` and `INSERT` privileges on `audit_log`, nothing else. It cannot `UPDATE`, `DELETE`, `TRUNCATE`, `ALTER` or disable triggers.

## 5. Retention

- **Account data** persists for as long as the account exists. Withdrawing deletes the account and crypto-shreds the vault.
- **Volunteer data** collected during the challenge window will be deleted **on 30 November 2026**, no later than ten days after the submission deadline, unless the clinical adviser and the ethics reviewer give explicit written approval to retain the aggregate for a specific follow-up. Individual-level rows are deleted even if the aggregate is kept.
- **Audit log** is retained through the submission window. In a production deployment, retention is a matter for the host organisation's governance.

## 6. What Sila will never do with genetic data

- Never send genetic data to any third party or external API.
- Never process it with an AI model. Every explanation on the app comes from a fixed template; the risk arithmetic is Mendelian and deterministic. No AI is used in the risk calculation and no AI is used to generate clinical text.
- Never use a shared outcome to recommend a reproductive or marriage decision.
- Never reveal, in the couple view, which partner carries what.
- Never retain plaintext results server-side. Decryption is in-memory and scoped to the request.

## 7. Production changes that this document would need

See [pilot-path.md](pilot-path.md) for what changes before this system could be used on real data. At minimum: in-country hosting where the local health-data regime requires it; cloud key-management or an HSM for the KEK; a real lab integration with its own auditability; ethics approval; a formal data protection impact assessment; and clinical governance.
